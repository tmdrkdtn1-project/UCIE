# UCIE 완전본 — 지정 고객 전용 상용 배포 계약 및 인수 로드맵

**확정 방향 (소유자 직접 지시, 2026-11-07):** UCIE의 목적은 **첫 번째 규칙 또는 데모를 출시하는 것이 아니라 네 가지 제품 목표를 모두 갖춘 완전본을 지정된 고객에게만 배포하는 것**이다. 배포 정책은 **고객별 비공개 상용 사용권(프로프라이어터리 계약)**을 기본으로 설계한다. 공용 오픈소스 공개 배포나 무제한 재배포는 출시 목적이 아니다.

**문서 상태:** 제품 요구와 검증 게이트의 인수 계약. 실제 라이선스 계약 체결, 배포 승인, 패키지 서명, 고객 설치 증거가 아니다. 이 문서는 운영 작업/수집/자동 승격을 시작하지 않는다.

**금지하는 완료 기준:** 첫 번째 규칙 서명, 2권의 미승인 초안, CI 녹색, Python wheel 임시 import, GitHub 브랜치 생성만으로 `UCIE_FULL_PRODUCT_RELEASE_GO`를 표시하지 않는다.

## 2. 지정 고객 전용 배포 구조

1. **공개 개발/기술 근거 영역:** 기존 `tmdrkdtn1-project/UCIE` 저장소는 지금 PUBLIC. 이미 공개한 코드의 접근 사실은 철회할 수 없다. 이 저장소와 공식 승인 출처만 현재 조사 범위에 사용한다. 보안 키, 계약, 고객명·고객 ID, 로그, 라이선스 토큰, 고객 코드는 절대 공개 저장소에 저장하지 않는다.
2. **상용 빌드 영역:** 소유자 통제의 별도 비공개 아티팩트 저장소/전달 경로에서 정확한 Git 커밋과 승인된 구성 요소로 서명된 고객 설치 번들을 만든다. 공용 PyPI, 공용 GitHub Releases, 무인 전 고객 다운로드 링크는 사용하지 않는다.
3. **고객별 라이선스:** 소유권·기여자 동의·서드파티 의무를 먼저 확인한 뒤 고객과 **비공개 상용 사용 계약**으로 제품, 좌석/장비, 기간, 지원, 업데이트, 재배포 제한, 계약 종료·회수 등을 확정한다. 라이선스 서명/검증과 고객별 실제 발급은 별도 보안 승인과 키 보관 절차가 필요하다. MIT/Apache 라이선스를 자동 추가하지 않는다.
4. **사용 환경 격리:** 공용 UCIE 공개 수집기는 승인된 공개 기술 근거만 다룬다. 고객 프로젝트 소스·대화·개인 자료를 전역 수집기로 올리지 않는다. 별도 고객 측 로컬 처리기가 필요한 경우 독립적인 권한·보관·검증을 새로 설계하고 승인받아야 한다.
5. **고객 설치·업데이트·해제:** 고객용 설치/제거, 독립 실행, 업데이트의 서명·버전 고정·안전 롤백, 비활성화·지원 프로토콜을 제공한다. 샘플·데모 키, 개발용 서명, 현재 9시 보고 스케줄러는 재사용하지 않는다.

## 4. 출시 로드맵과 명시적인 통과 조건

### C0 — 4축 완전성 기능 목록과 수용 기준
모든 코드/사용자 화면/기능을 `IMPLEMENTED`, `SYNTHETIC_TESTED`, `REAL_END_TO_END_TESTED`, `SECURITY_RIGHTS_CLEARED`, `CUSTOMER_ACCEPTED`로 **각각** 기록. 네 축의 최소 고객 업무를 1개씩 독립 환경에서 처음부터 끝까지 실제 완료해야 한다. 미승인 초안 기능은 반드시 남은 작업으로 표시.

### C1 — 완전본 스테이징 번들
wheel **외**에 실제 고객 실행에 필요한 서비스/CLI/UI, 승인된 도서관 내용·SkillBook 산출물, Windows 실행 지침, 설치/제거/업데이트 도구, 설정 스키마, 보안/권리 고지와 필요한 첫 번째 실행 절차까지 목록 고정. 필요성 검증 없이 개발용 원장·백업·DB·테스트 데이터·키·고객 정보는 포함 금지. 누락/위변조가 있으면 설치 전에 차단.

### C2 — 제품 보안·권리·품질 인수
실제 코드 권리자, 기여자 동의, 승인된 공개 근거 사용 범위와 서드파티 라이선스/NOTICE/SBOM 검토. Python·PowerShell·Windows/Git·MCP/API 버전별 기능/회귀/권한 테스트. 고객 별 코드·데이터 경계/서비스 네트워크 정책을 검증. 기존 첫 규칙 위험 수용 승인으로 V1 전체 보안·법적 결정을 대체하지 않는다.

### C3 — 고객 전용 서명/라이선스/전달
고객 식별정보는 **공개 UCIE 저장소 밖**, 접근 통제된 시스템에만 보관. 소유자 제품 서명 키는 CI나 대화로 반출 금지. 고객별 계약/권한/버전/만료·갱신·회수, 고객별 수신 검증, 무결성 증거를 결속. 고객 인증서/서명 키 관리와 라이선스 발급·회수는 실제 검증 전까지 NO_GO.

### C4 — 실제 고객 파일 없이 격리된 수신자 리허설
별도 깨끗한 UCIE 테스트 환경에서 설치→4축 사용→라이선스 제한→업데이트→롤백→제거→재설치까지 인수. 테스트에는 UCIE 작성 합성 공개 데이터만 사용하며 고객 프로젝트에 접근하지 않는다. 각 단계에 실제 CI·실행 영수증과 실패 처리 기록 확보.

### C5 — 지정 고객 1곳의 제한 배포 및 확산
실제 고객 계약/권리·고객별 수신 승인 후에만 배포. 배포 번들 SHA256, 서명 키 공개 지문, 릴리스 일련번호, 소유자 승인, 고객 수신·설치·실사용 확인, 문제 발생 시 롤백 경로를 결합. 첫 고객의 PASS 없이 다수 고객 배포 금지.

## I. 최종 제품 목적 — 동등한 4대 축

1. **코딩 오류 예방:** 오류 원인·안전한 수정·영향 버전·회귀시험·예방 규칙 개발.
2. **개발/유지보수 엔진·스킬·학습 엔진 로직 발굴 및 개선:** 오류 사례에만 한정하지 않고 유용한 개발 방법·알고리즘·자동화 및 유지보수 기술을 비교·평가하여 일반화.
3. **범용 분류 가상도서관:** 어떤 종류의 프로젝트든 필요한 승인된 범용 엔진·스킬·학습 로직·오류 규칙을 검색·비교·독립 반출·재사용.
4. **지식과 경험 기반 지속 진화:** 위 세 활동 및 UCIE 자체의 허용된 시험·개선 경험을 축적하여 도서관의 검색·품질·기술 능력을 발전.

가상도서관은 제품의 중앙 기반이며 네 번째 축의 진화 폐회로가 매 사이클로 돌아온다. **오류 규칙 수를 계속 늘리는 것이 최종 목표가 아님.**

## II. 반드시 필요한 두 기반 시스템

### A. 외부 공급원 발굴·선정·승인 카탈로그 (P1)

공개 기술 문서·릴리스·보안 권고 및 API·사이트·소프트웨어·데이터셋의 유용성을 평가하는 레지스트리:
- 고정 출처 ID, 발행자·소유자, 공식/독립 제3자 구분, 정확한 공개 주소
- 제공 자료(오류 예방 / 엔진 / 스킬 / 학습 로직 / 시험 / 버전), 인터페이스 유형(API / 공식 문서 / 허용된 웹 자료 / 공개 메타데이터)
- 사용권·라이선스·삭제 및 opt-out 조건, 수집 가능 범위, 요청 빈도·쿼터, 개인정보/비밀정보 배제
- 승인 상태: `ACTIVE_APPROVED`, `RESEARCH_ONLY`, `BLOCKED`, `RETIRED` — 비승인 공급원은 어떠한 네트워크 요청에도 자동 반영 금지
- 소스 계보와 날짜·버전·커밋·PR·신뢰도/불확실성

**현행 승인:** 공식 공개 기술 문서/릴리스/보안 권고 및 `python/cpython`, `PowerShell/PowerShell`, `git/git`, `modelcontextprotocol/python-sdk`, `actions/runner-images`만. 추가 저장소/사이트의 수집 승인 없음. GH Archive, Software Heritage, SWE-bench, The Stack v2는 **향후 평가 후보**일 뿐 현행 크롤링·수집 허가가 아니다.

### B. 범용 자동수집 모듈 (P2)

- 공통 Adapter 계약: `source_id`, `allowed_endpoint`, `cursor`, `fetch_budget`, `content_kind`, `revision_hash`, `observed_at`, `license_scope`, `result_status`.
- GitHub 기존 Stage10/13/14/15 수집 경로를 재사용, 한 번에 모든 모듈 교체 금지.
- API 우선, 명시적으로 허용된 외부 웹 자료만 규칙과 접근 정책에 맞춰 수집. 페이지 갱신·중복·역사 자료·추출 실패 처리. 원본 대량 재배포 금지.
- 증분·중복 제거·중단 후 재개, 시간당 호출 예산, 실패 시 분리 기록. 수집=지식 승인 아님.
- 기본 경계: 승인되지 않은 소스 자동 활성화 금지, 기존 Windows 스케줄러 중복 등록 금지.

## III. UCIE 가상도서관 카탈로그

분류: `PREVENTION_RULE`, `DEVELOPMENT_ENGINE`, `REUSABLE_SKILL`, `LEARNING_LOGIC`, `TEST_RECIPE`, `UCIE_EXPERIENCE`.

각 항목: ID, 분야·목적·태그, 사용 조건/입출력/의존성, 언어/플랫폼/영향 버전, 공식 출처·소유자·날짜·커밋·해시·사용권, 미검증/시험/승인/폐기 상태, 관련 항목/상위개정/후속개선, 테스트 근거, 승인 후 반출 가능한 버전 고정 산출물. 추출·사용·실험 경험은 `UCIE 자체의 승인된 공개/합성 실험`만 연결하고 외부 프로젝트 경험은 절대 유입하지 않는다.

도서관 MVP는 **검색 → 비교 → 출처·제약 확인 → 승인된 산출물 선택·반출**까지 가능해야 한다. 단순 SQLite 파일이나 PR 목록을 도서관 완성으로 보지 않는다.

## VI. 바로 다음 개발 묶음 — 프리뷰

### 배치 1 (즉시 착수): W01 + W02, W05 설계 연결

1. **W01: Source Registry V1** — 허용된 GitHub 5개/공식 문서 유형을 별도 카탈로그로 코드화. `ACTIVE_APPROVED`와 `RESEARCH_ONLY`를 구분하고 외부 추가 요청이 없는 한 무허가 GET·새 URL 조회 없음.
2. **W02: Virtual Library Entry V1** — `kind/id/domain/language/runtime/dependency/provenance/license/verification/lifecycle/evidence_sha` 및 공개 출처 계보 계약을 정의. 현재 SQLite 원장은 변경하지 않음.
3. **W05 설계 접점** — 스킬·엔진·학습 로직 후보의 평가 필드/분류 체계를 W02 계약에 연결하되 데이터 없음에 PASS/승인 표시하지 않음.

**인수 조건:** 공통 JSON 샘플 1건씩(공식 문서 / 공개 엔진·스킬 후보 / 오류 예방), 공급원 승인 검사, 임의 소스 거부, 로컬 실행이나 API 호출 없이 결정적 결과, 새 변경 파일 범위의 CI 통과.

### 배치 2: W03 + W04 + W05 구현

기존 `public_discovery.py`, `public_external_history.py`, `public_candidate_learning.py`, `latest_hourly_review.py`, `skill_profiles.py` 재사용. 실제 승인 출처만 허용. 검색은 먼저 표준 라이브러리/SQLite 읽기전용 인덱스에서 시작하고 추가 벡터/모델 인프라는 V1 필수로 삼지 않음.

**인수 조건:** 허용 데이터로 `개발 작업/언어/스킬/영향 버전` 검색이 동작하고 정확한 출처와 후보 상태가 노출될 것. 같은 자료를 신규 최신 이슈로 오분류하지 않을 것.

### 배치 3: W06~W10 제품 통합

안전한 평가·재사용 가능한 패키징·UCIE 자체 경험 학습을 연결. 승인과 무관한 자동 승격/서명/배포는 하지 않는다. UI는 핵심 검색·반출 흐름을 완성할 때 최소 인터페이스부터 시작.

## VII. 개발 중단/보류 기준과 일정 운영

- 기존 오류 8·9번째 새 규칙 개발을 **상시 우선순위에서 제외**. 고객 가치가 명확한 중요 신규 공개 근거만 조사·승격 검토.
- 이미 통과한 기능의 중복 CI, 중복 Stage, 무의미한 재현은 중단. **새 변경의 필수 회귀시험만** 수행.
- 현행 시간당 공개 수집은 기존 예약작업을 유지. 새 스케줄러, 자동 규칙 승격, 미승인 API 확장은 금지.
- 다른 프로젝트 코드·비공개 데이터·연결 앱·대화·로그와 프로젝트별 경험은 절대 수집하지 않는다.
- 서명/배포·오픈소스 라이선스 판단, 외부 격리 평가 등 실제 필요한 승인 경계는 유지하되 모든 후보에 같은 QA를 반복 수행하지 않는다.
- 작업 진행 보고는 **기능 묶음 단위 1회**: Git commit/PR, 변경 파일, 기능 인수 결과, 남은 블로커, 다음 작업자.

## VIII. UCIE V1 최종 인수 시나리오

1. **승인된 공급원에서 자동 수집**하고 최신·역사 자료를 구분.
2. 오류 규칙 뿐 아니라 **유용한 개발 엔진·스킬·학습 로직**을 추출·분류.
3. 가상도서관에서 **목적/언어/버전/기술**로 검색·비교하고 근거·제약 확인.
4. UCIE가 작성한 시험으로 실제 검출·작동/개선 효과 확인.
5. 허용된 일반화 산출물을 **명시적으로 승인·서명 후** 독립 프로젝트 소비자에게 배포 가능.
6. 같은 소스 또는 새로운 공개 근거와 UCIE 자체 실험으로 **지식이 개선·개정되는 폐회로**를 실증.

이를 모두 관찰해야 `UCIE_V1_ACCEPTED`라고 부른다. 문서/코드 목표 선언, 샘플 테스트 PASS, 미검증 원장 증가만으로 V1 완료를 선언하지 않는다.

## 1. 말투 기준

- 기본: **낯선 사람에게 설명하는 짧은 존댓말**. 쉬운 명사, 하나의 동사, 한 문장에서 하나의 뜻. 지시하거나 평가하지 않고 선택권과 다음 행동을 알려 준다.
- 고객은 Python/MCP/SDK/PR/Git/CLI/SHA/버전의 의미를 모를 수 있다. 설명 전에는 이 단어를 첫 화면 주요 문구나 버튼에 사용하지 않는다.
- 기술 용어가 필수인 경우 쉬운 뜻을 **바로 옆에서** 알려 준다. 사용자가 직접 '자세히 보기'를 선택했을 때 원본 영문 기술 용어·시험·권리 정보를 보인다.
- '고쳐 드립니다', '100% 안전', 'AI가 분석했습니다', '원인 확인 완료' 금지(실제 구현/독립 검증 없는 상태). '가능성이 있어요', '비슷한 공개 사례가 있어요', '여기까지 확인됐어요'는 근거가 있을 때만.
- 오류 처리에서 사람을 탓하지 않는다: '잘못 입력했어요'보다 '문제 상황을 조금 더 짧게 적어 주세요'. 기술 내부 오류 코드를 사용자에게 그대로 보여주지 않는다.
- 영어 원문·고정 API 식별자는 사라지지 않는다. '공식 자료 보기'의 내부 상세/복사 영역에서 정확히 유지한다. 번역 때문에 기술 진실을 바꾸지 않는다.
- 이름이 쉬워져도 실제 작동 기능을 확장하지 않는다. '확인 방법 보기'는 실제 고객 코드 진단이나 수정이 아니다.

## 3. 고정된 주요 메뉴와 대체 메뉴의 위치

**현행 V04 실제 메뉴/링크는 그대로 둔다**. 아래는 별도 시안에서만 비교할 후보 이름이다.

| 현행 메뉴 / 기술 경로 | 초보 사용자 시안 이름 | 기본 화면에서 기대하는 일 |
| --- | --- | --- |
| 홈 (/local) | 홈 | '지금 어떤 도움이 필요하세요?' |
| 문제 예방 (/local/error) | 문제 살펴보기 | 증상과 원인 확인 방법, 실제 수정은 아님 |
| 개발 도구 (/local/engine) | 예제 체험 | UCIE가 준비한 안전한 입력으로만 실행 |
| 라이브러리 (/local/library) | 쉬운 설명 | 따라 읽는 기술 자료와 예제 |
| 개선 제안 (/local/evolution) | 바뀐 기술 살펴보기 | 공용 기술 변화 검토, 내 프로젝트는 아님 |
| 이용 안내 (/local/policy) | 도움말 | 무엇을 할 수 있고 무엇을 못하는지 |

'문제 해결'이라는 이름은 **자동으로 해결해 준다**고 생각하기 쉬우므로 기본 후보로 삼지 않는다. 1차 사용자 시험에서 '문제 살펴보기' 의미도 모호하면 '문제가 생겼어요'로 검토한다. 기존 4축 제품 기능은 내부 구조로 그대로 유지한다.

## 4. 화면별 실제 텍스트

### A. 처음 들어왔을 때

제목: **지금 어떤 도움이 필요하세요?**
설명: '지금 필요한 도움을 골라 보세요.'
선택 1: '코드가 잘 안 돼요' / '오류가 났거나 실행이 안 될 때, 확인할 방법을 찾아볼 수 있어요.' / 버튼 **'문제 살펴보기'**
선택 2: '간단한 예제를 보고 싶어요' / '미리 준비된 예제로 어떻게 동작하는지 볼 수 있어요.' / 버튼 **'예제 체험하기'**
선택 3: '차근차근 배우고 싶어요' / '쉬운 설명과 예제를 찾아 읽을 수 있어요.' / 버튼 **'설명 읽기'**
범위 고지: '현재는 일부 대표 문제와 준비된 예제를 안내해요. 새 앱을 자동으로 만들거나 사용 중인 코드를 직접 고치지는 못해요.'
보조 링크: **'지금 할 수 있는 일 보기'**

### B. 질문 입력

제목: **어떤 일이 있었나요?**
입력 라벨: '문제 상황을 1~3문장으로 설명해 주세요 (12~360자)'
자리표시 예: '파이썬에서 모듈을 찾지 못한다고 나와요.'
안전 안내: '코드, 오류 로그, 파일 경로, 비밀번호, 개인 정보는 입력하지 마세요.'
버튼: **'확인 방법 찾아보기'**
보조 링크: '대표 문제에서 고르기'
고정 제한: '현재는 네 가지 대표 문제만 안내할 수 있어요.' — 자세한 범위를 실제 라우트 기능과 동일하게 유지.

### C. 유사 문제를 찾은 경우

제목: **비슷한 문제를 찾았어요**
설명: '적어 주신 상황과 비슷한 공개 사례가 있어요. 실제 원인이 같은지는 아직 확인하지 못했어요.'
본문 제목: '먼저 확인해 볼 일'
버튼: **'확인 방법 보기'**
근거를 직접 보려는 사용자: '왜 이렇게 안내하나요?'
잘못 해석하지 않도록 '내 컴퓨터나 코드를 직접 검사하지 않았어요.' 명시.

### D. 찾지 못한 경우

제목: **아직 이 문제에 맞는 안내가 없어요**
설명: '지금은 몇 가지 대표적인 문제만 안내할 수 있어요. 비슷한 상황을 아래에서 골라 보세요.'
주 버튼: **'대표 문제 보기'**
보조 링크: '다른 말로 설명하기'
코드 작성/생성형 AI/검색 성공에 관한 허위 약속 금지.

### E. 정보가 너무 많거나 안전하지 않을 수 있는 입력

제목: **문제 상황만 짧게 적어 주세요**
설명: '코드나 로그, 파일 주소, 비밀번호 대신 화면에 어떤 문제가 나타났는지 적어 주세요.'
보조: '12~360자로 적어 주세요.' 민감 정보를 감지하는 기술 방어가 완벽하다고 주장하지 않음.
사용자 원문을 오류창·로그·URL·Slack 등에 반사하지 않음.

### F. 예제 시험 결과

제목: **준비된 예제에서는 이렇게 나왔어요**
설명: 'UCIE가 준비한 입력으로 확인한 결과예요. 지금 사용 중인 코드에서도 똑같이 되는지는 확인하지 않았어요.'
주 링크: **'예제가 하는 일 보기'**
선택적 상세: '실제로 시험한 범위 보기'
'내 코드도 고쳐졌어요' 금지.

### G. 확인한 기술이 오래되었거나 내 버전을 모를 때

제목: **지금 쓰는 프로그램에서도 될지는 아직 몰라요**
설명: '확인한 프로그램 번호가 다르거나 알려져 있지 않아요. 바로 적용하기 전에 확인이 필요해요.'
주 버튼: **'확인된 조건 보기'**
버전 선택에는 '모르겠어요' 허용, 하지만 안전 판정 승격 없음.

### H. 라이선스·배포 승인이 없는 콘텐츠

제목: **설명은 볼 수 있지만, 다른 사람에게 제공하는 것은 아직 안 돼요**
설명: '이 자료는 참고할 수 있어요. 설치하거나 배포할 수 있는지는 따로 확인해야 해요.'
버튼: **'주의할 점 보기'**

### I. 새 공개자료를 볼 수 없을 때

제목: **지금은 새 자료를 확인할 수 없어요**
설명: '이전에 찾아본 자료가 있으면 보여드릴게요. 새로 바뀐 내용이 없는지는 아직 알 수 없어요.'
버튼: **'이전에 확인한 자료 보기'** (실제 기록이 있을 때만)
인터넷 연결 없이 현재 버전 확정이라고 주장하지 않음.

### J. '만들고 싶은 게 있어요' — 미래 기능 전용 문구, **현재 UI 사용 금지**

미래 상용 완전본 고객의 중요한 출발점은 '무엇을 만들고 싶어요'이다. 이 기능은 아직 없으므로 지금 버튼·검색창·홈에 표시하거나 클릭 가능하게 만들지 않는다. 추후 권리·기능·개인정보 보호·지원 범위가 실제로 검증된 뒤에만 다음 표현을 검토한다.

미래 제목: '무엇을 만들고 싶으세요?'
미래 설명: '원하는 기능을 말로 설명해 주세요. 지금 안내할 수 있는 부분부터 찾아볼게요.'
미래 결과: '지금은 이 부분을 도와드릴 수 있어요' / '이 부분은 아직 안내하지 못해요'.
**금지:** '원하는 앱 완성', '코드 자동 생성', '모든 분야의 코딩 가능' 등의 포괄적 약속. 현재 허용된 기술 범위를 벗어나면 명확하게 지원하지 못한다고 안내한다.

## 5. 초보자에게 보이지 않는 전문 원문(반드시 보존)

상세 페이지에서 사용자가 선택해서 펼칠 수 있어야 함: 정식 기술명, 소스 revision/commit/blob SHA, 실험/시험 환경, positive/negative/control, 라이선스/권리·독립 승인, 재현 레시피 및 기계 계약. 이 정보는 없애는 것이 아니라 **기본 화면에서 접는 것**이다.

특히 'UCIE가 시험했습니다'와 '실제 고객 환경에서 확인됐습니다'와 '다른 사람에게 제공할 권한이 있습니다'는 서로 다른 사실이다. 사용자 친화 표현으로 바꾸더라도 이 차이는 유지한다.

## 6. 화면 카피 QA 및 승인 조건

- 초보 이용자 실제 언어 이해: 처음 코딩하는 사람이 사전 설명 없이 제목·버튼의 의미를 답할 수 있는지. 목표: 시작 10초 내 적절한 진입 버튼 선택률 80% 이상(실측 전 가정).
- 모든 주요 문구를 '이 버튼을 누르면 무슨 일이 일어나나요?' 질문으로 검토. 실제 기능이 불가능한 약속을 했다면 FAIL.
